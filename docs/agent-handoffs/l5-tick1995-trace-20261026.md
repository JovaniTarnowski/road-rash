## Lane-validity section: a real port gap, not this trigger

Reading the FULL 0x0044e710 decompile revealed an unconditional
lane-validity block (no obstacle gate) that native does NOT port: for
even kinds it checks whether the current lane fits the slice's lane
count and, if not, nudges the lane toward validity (with a
set-target-0/stop branch in one sub-path). Native `plan_speed` has ONLY
the obstacle-gated lane change, so this whole section is missing — a
genuine gap worth its own plan-16 task. It does NOT explain tick 1995:
a scratch probe (`leftlanes` at the car's sample 341) shows
leftlanes=2 while the car holds lane -2, so the gate
(`LEFTCOUNT < -lane`, i.e. 2 < 2) is false and the section is a no-op
for this exact state. (Caveat filed: the gate reads the slice at
native +0x50-equivalent; native has no +0x50 image, and the probe used
the car's current sample. If +0x50 ever points elsewhere, re-evaluate.)

## Why L5b can't replay (launch jitter, not a bug)

L5b differs from L5 in 36 frame-0 keys, ALL rider brain speed words
(rider.1/10 +0x19c/+0x1a4/+0x1bc/+0x1c0/+0x1c4...). This is the documented
run-varying launch jitter (`srand(time(NULL))` at WinMain; 0x004078f0
jitters personality level speeds before the race seed anchors RNG).
Everything else (positions, speeds, RNG stream, cars, nodes, ring) matches,
so L5b is a valid independent instance — but native's deterministic setup
models L5's jitter outcome, not L5b's, so L5b cannot serve as a replay
golden. It remains valuable as (a) proxy-extension validation (new keys
dump correctly), and (b) independent confirmation of the removal-run
signature with full internal state.
Narrowed further: the differing words match the `rand()%100` name-roll
outcome (0x00402e10: roll 42 → "Honest Phil" row set, 69 → "Veldaar",
else default rider names via 0x00402d60) selecting different personality
rows for riders 1 and 10 — same draw count (RNG stays in sync), different
rows. Verified the frontend session's proxy changes cannot cause this:
the menu watchdog thread is created only when RR_ORACLE_MENU is set
(gated), and the build change is link-flags only. The open question this
leaves for the integrator is how native's deterministic setup lands on
L5's jitter outcome (spare-levels path vs replay-harness seeding); it is
orthogonal to the car divergence and does not block it.

## Car mover identified: 0x0043adc0 (REA, no code changes)

`0x00475698+0x0c` = `0x00446830` (draw), `+0x10` = `0x0044e710`

dispatcher, no position/speed/lane math of its own. If `+0x160 == 0`,
zero `+0x114`/`+0x118`/`+0x164`; then unconditionally call

## Lane-word writer: 00454240 ring fill (REA + disassembly, no code changes)

REA 6.4.0 `function 0x004528f0` (exit 0, 47 bytes): a stateless
read-through, NOT the `+0x2c/+0x30` writer. It reads input
`+0x00` (null check), `+0x14`/`+0x18` (SAR 8), and writes only its
two caller out-pointers: `0x200/0x200` when input is null, else
the two downshifted words. The `+0x2c/+0x30` stores happen in the
callers: 7 sites inside `0x00453030` and 1 site inside
`0x00454240` (ring fill). Disassembly at the ring-fill site
(`0x4542f3-0x454302`): out-pointers are `edi+0x30` and
`edi+0x2c` (a ring slice struct), input is `ebp+0x10` (the NALR
record). So ring-slice lane words are written at build time
from NALR, defaulting to 512/512 on null -- and native already
ports that default (`course.cpp:127`). What native does NOT
model: behind the ring back, the original slot keeps whatever
was last written or reused (256 in the traced removals), while
native reads the static current route (512 at Napa-394).
Proving the exact slot-identity/update rule needs ring-builder
(`0x00454240`-class) RE, which is plan-17-scale work and is NOT
started here. First recon (REA exit 0): `0x00454240` is 1159
bytes building ONE scrolling-window slice record per call
(called per-slice by `0x00454c80`), with the single
`0x004528f0` call writing the fresh slice's `+0x2c/+0x30`.
So fresh in-window slices always carry current NALR words; the
removal-tick staleness comes from the car reading a slot the
builder has stopped refreshing (behind-back), not from the
builder writing wrong values.

### Supporting timing (read-only TSV)

Builder recon (REA 6.4.0 `0x00454240`, exit 0): the writer itself
is unconditional -- one `0x004528f0` call per built slice writes
`+0x2c/+0x30` with no skip, null, or window check at the site
(null handling lives inside `0x004528f0`, which defaults both
words to 512). Disassembly of the eviction path
(`0x454d9d-0x454de2`): dispatch on ring-slot `+0x2c` small-int
state (1/2/4/default), victim slot self-relinked
(`[eax+0x8..+0x14] = eax`). So the ring is a fixed slot array
repurposed as it scrolls; the car's spawn-sample slot pointer
(`+0x2c` == `+0x140`, verified identical in all 5388 L5e dumps)
keeps pointing at its slot after the window leaves it behind --
reads then return whatever the slot was rebuilt with (256 in the
traced removals). Porting that requires the ring allocator +
rebuild schedule (plan-17 work), explicitly out of scope here.

Slot-index hypothesis (read-only probe, since reverted): ring
span is exactly 0x8000 Q8 = 128 samples, so a mod-128 slot
mapping predicts the behind-back car's slot holds the newest
in-window sample with the same residue: L5e-2399 (car 394,
window [403,531]) predicts sample 522's words; L5e-2089 (car
336, window [337,465]) predicts 464; L5-1133 (car 159, window
[160,288]) predicts 287. A temporary native-route probe (L1
replay, since reverted) confirmed route[287] = 512/512,
matching the observed slot flip 256->512 there. route[522]
and route[464] were never visited by L1 cars, so the
predictions there are untested -- the discriminating check is
pending (needs a route-lane dump at those samples or a capture
with cars there).

Per-life word changes coincide with ring-window crossings, not
car motion: 13e2248 ticks 2339 (in-window, 256->512) and 2361
(car sample 394 falls behind back 395, 512->256); 13e2038 tick
2089 (sample 336 falls behind back 337, 512->256); 13e1c18 tick

per-car slice slot refreshed from the route while in-window

car leaves the window -- the removal runs then read whatever the

## Slice-pointer topology (read-only TSV statistics, no code changes)
