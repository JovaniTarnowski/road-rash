## Corroboration (same night, no Wine needed)

- REA 6.4.0 `function 0x44e710` returns pseudocode WHITESPACE-IDENTICAL to
  `analysis/decompiled/0044e710.c` (10,216 chars). The whole plan_speed
  port (gate, 1f8 decrement, cruise, latch, obstacle scan, lane gates,
  follow, signal/stop-line, halving, 0x00449880 approach call) is
  independently confirmed. 0x00407a90 and 0x0044efa0 have NO REA procedure
  entry (scheduler-dispatched pattern, known gap #8); those rest on the
  project export + disassembly.
- 0x0044efa0 disassembly (44eff1-44f031): the 0x1f8 setters (0x3c/0xf0)
  run ONLY for odd-kind cars (`testb $0x1,%al; je` skips evens); native
  gates identically. A full-disassembly grep shows NO other car +0x1f8
  setter (other hits are rider-half finish-distance words). m1f8>0 is
  impossible for this kind-2 car in both binaries.
- 0x00449880/0x004498c0 disassembly: speed = speed + dt*rate, clamped
  DOWN to target (`cmp; jge done; else speed=target`) — exactly native
  line 359's `min()`. No brake-to-zero special case; with target=cruise
  the speed can only rise toward cruise.
- 0x0044dc10 (think gate) returns nonzero for road cars (kind gate at
  top); plan runs in both worlds.
- Full node multisets at tick 1995 (scratch RR_DUMP_ALL gate, reverted)
  match EXCEPT the single car pair — no hidden ped/signal/controller/
  parked divergence. No active peds in either world.
- m108=-1440 explained (benign): exact-backward heading (atan2 yields
  exactly 0x80 when steer error>>8 == 0 with negative drift) feeds the
  sine branch: -1.0 * ec = -speed. Consistent with oncoming (-direction)
  travel; the -261 then follows exactly from term arithmetic
  ((2*-1440+660)*60>>9 = -261). Native move math is self-consistent.
- Full native pre-move state dumped at the diverging tick (scratch PLAN
  probe, reverted): pos=87366 spd=1528 dt=60 tgt=21 rate=15 sig=-1
  lane=-2 lat=-96000 ph=217 gap=1000 win=78 fol=0 hur=0 obs=0 m108=-1528

  reproduces the native result exactly (min(2100,2428)=2100; drag 11;

  ported pipeline is deterministic-identical to itself; the golden

  shape the verified move math cannot produce from these inputs.

## Hydrated-mode probe (attempted, no conclusion — diagnostic-only as documented)

`RR_FIELD_IGNORE_CARS=1 RR_FIELD_CARS_FROM_GOLDEN=1` run to isolate the car:
diverges at frame 631 (tick 632), `rider.8.brain_194` (ai_target_x)
original -11008 vs native -15386. This does NOT indicate a second bug and
does NOT isolate the car:

- `load_cars` pairs golden slots (sorted by pool ADDRESS) with native cars
  (sorted by SERIAL). Pool realloc on spawn reshuffles addresses on either
  side independently, so the pairing can silently swap cars; the multiset
  compare in `cars()` is swap-proof, the hydration copy is not.
- Hydration copies only pos/lat/spd, leaving native motion words
  (m108/sign, signal latch, steer_error, lane) under golden positions —
  a mixed state the original never has, which AI planning reads
  (obstacle v108, lane gates). Any brain difference after that is
  artifactual by construction (`SIM_SCENARIOS.md`: hydrated runs "do not
  establish native traffic parity" and "never report identical").
- In the non-hydrated run every AI brain field matches through tick 1994,
  so AI planning inputs (including traffic as observed) are faithful up to
  the car tick.

No tree changes were made (env-var-only run). Do not use hydrated mode to
argue for or against the tick-1995 mechanism; it remains what the doc
says: a cadence diagnostic.
